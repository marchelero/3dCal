## 1. Goal

Hoy `BrandSelectorField` (`lib/shared/widgets/brand_selector_field.dart`) usa una sola constante `kKnown3dBrands` (21 marcas mezcladas: Creality + eSun + Voron + Hatchbox + Bambu Lab + Prusament + …) y observa **ambos** notifiers (`filamentsNotifierProvider` **y** `printersNotifierProvider`) para mergear marcas registradas. Eso significa que al usuario que está registrando un filamento se le ofrece "Voron" o "Voron Design" como opción de marca — cuando Voron no vende filamentos. Y al revés: al registrar una impresora aparece "eSun" o "Hatchbox", que son marcas de filamentos.

Además, los dos forms (`filament_form_page.dart`, `printer_form_page.dart`) piden primero el **Nombre del modelo** y después la **Marca**. La lógica mental es al revés: el usuario primero sabe qué marca tiene, y después identifica el modelo dentro de esa marca.

Este feature separa los universos de marca (filamento vs. impresora) y reordena los forms para que la marca se elija primero.

## 2. User Story

**Como** maker/operador de impresión 3D que está registrando equipo en la app por primera vez (o agregando uno nuevo desde Ajustes → Catálogos)

**Quiero** que (a) el selector de marca de filamento me muestre solo marcas de filamentos, (b) el selector de marca de impresora me muestre solo marcas de impresoras, y (c) tanto en el form de filamento como en el de impresora, primero elija la marca y después ingrese el modelo

**Para** no perder tiempo descartando opciones que no aplican a lo que estoy registrando y para que el modelo se piense como "segundo paso" dentro de la marca ya elegida.

### 6.2 API del widget — Parametrizar con enum (recomendado, sujeto a Q3)

**Decisión recomendada**: parametrizar `BrandSelectorField` con un enum `BrandDomain`:

```dart
// Pseudo-codigo (NO es implementacion, es diseno)
enum BrandDomain { filament, printer }

class BrandSelectorField extends ConsumerStatefulWidget {
  const BrandSelectorField({
    required this.domain,  // NUEVO: required
    required this.controller,
    this.validator,
    this.label,
    this.helperText,
    this.enabled = true,
  });
  final BrandDomain domain;
  // ... resto igual
}
```

**Justificación**:
- **Pros**: una sola implementación, type-safe (imposible pasar dominio equivocado), fácil agregar `BrandDomain.resin` o `.tool` en el futuro, ~80% del código compartido (overrides de `_registeredBrands` y `_options`).
- **Contras**: el call site debe pasar el dominio explícitamente (es un cambio de firma → requiere migración de 4 call sites).

**Alternativa descartada**: dos widgets separados (`FilamentBrandSelectorField`, `PrinterBrandSelectorField`). Más explícitos pero duplican ~80% del código y son inflexibles ante nuevos dominios.

### 6.3 Reorder del form

**Antes** (en `filament_form_page.dart`):
```
[ Nombre (TextFormField) ]
[ Marca (BrandSelectorField) ]
[ Precio ]
[ Gramos ]
[ Switch default ]
```

**Después**:
```
[ Marca (BrandSelectorField, domain: filament) ]  ← NUEVO PRIMERO
[ Nombre (TextFormField, "Ej: PLA Negro / PLA Premium") ]
[ Precio ]
[ Gramos ]
[ Switch default ]
```

**Justificación**: el placeholder del campo nombre se mantiene, pero el helper text puede actualizarse para reforzar que el modelo va "dentro" de la marca (ej: "Modelo dentro de la marca seleccionada" — opcional, ver Q7).

**Idem** para `printer_form_page.dart` con `domain: printer` y el helper del campo modelo cambiando a "Modelo de la marca seleccionada" (opcional).

### 6.4 Initial config (IS-5)

Las dos invocaciones en `initial_config_page.dart` (paso 2) cambian de:

```dart
// Actual
BrandSelectorField(controller: _printerBrandCtrl, label: EsBO.filamentBrand, ...),
BrandSelectorField(controller: _filamentBrandCtrl, label: EsBO.filamentBrand, ...),
```

A:

```dart
// Nuevo
BrandSelectorField(domain: BrandDomain.printer, controller: _printerBrandCtrl, ...),
BrandSelectorField(domain: BrandDomain.filament, controller: _filamentBrandCtrl, ...),
```

**Sin otros cambios** en `initial_config_page.dart`. El reorder de inputs dentro del form de impresora/filamento del stepper se aplica después en FEATURE 2.

## 8. Migration / Breaking Changes

- **Sin migración de schema Drift**: las tablas `Filaments` y `Printers` ya tienen `brand` nullable desde v1. No se requieren migraciones.
- **Sin cambios en la API de los notifiers**: `create()`, `update()`, `setAsDefault()` mantienen sus firmas (incluyendo el orden de argumentos).
- **Cambio de firma en `BrandSelectorField`**: pasa de `(controller, label?, helperText?, validator?, enabled?)` a `(domain [required], controller, label?, helperText?, validator?, enabled?)`. **Breaking para call sites** — los 4 call sites conocidos se actualizan en este mismo PR:
  1. `lib/features/catalog/filaments/presentation/pages/filament_form_page.dart`
  2. `lib/features/catalog/printers/presentation/pages/printer_form_page.dart`
  3. `lib/features/onboarding/presentation/pages/initial_config_page.dart` (x2: sub-sección impresora, sub-sección filamento)
- **Cambio de comportamiento observable**: el orden de campos en los forms cambia (AC-003, AC-004). Esto es intencional y verificado por tests.
- **No hay datos que migrar**: el orden de los inputs no se persiste en la BD.

El form de impresora (`printer_form_page.dart` línea 140) actualmente pasa `label: EsBO.filamentBrand` ("Marca"). Esto es funcionalmente correcto (la palabra "Marca" sirve para ambos), pero conceptualmente es confuso. **Recomendación**: en este mismo PR (sin costo), crear la key `printerBrand` con el mismo valor `"Marca"` / `"Brand"` para que cada form use su key semánticamente correcta.
