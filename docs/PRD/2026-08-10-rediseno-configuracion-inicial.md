## 1. Goal

La pantalla `InitialConfigPage` (`lib/features/onboarding/presentation/pages/initial_config_page.dart`, 889 líneas) hoy es un stepper funcional de 3 pasos:

1. Idioma (SegmentedButton ES/EN) + Moneda (DropdownButtonFormField 15 monedas).
2. Impresora (BrandSelectorField + nombre + watts, **requerida**) + Filamento (BrandSelectorField + nombre + precio + gramos, **opcional**, con botón "Lo agrego después").
3. Ganancia % (default 200, rango 0–1000) + Tarifa kWh (default 0.7, rango 0.10–5.00).

Luego → 4 slides de marketing en `OnboardingPage` (`lib/features/onboarding/presentation/pages/onboarding_page.dart`) → home `/`.

**Problemas identificados** (de la lectura del código y del brief):

1. **Fricción inicial alta**: el paso 2 mete DOS formularios casi completos (impresora + filamento). En mobile se siente como "registro web".
2. **Stepper custom (líneas 556–662)**: `_StepperIndicator` con círculos + líneas animadas — detallado pero **no es un LinearProgressIndicator nativo de Material 3**, lo que rompe la coherencia con el resto del design system (que ya usa M3 en `app_theme.dart`).
3. **Sin contexto del "por qué"**: cada sección es un label + helper. No hay microcopy que explique por qué se pide cada dato (ej: "La tarifa eléctrica se usa para calcular el costo de energía de cada impresión").
4. **Sin preview del cotizador**: el usuario llena 6 inputs a ciegas. Termina el onboarding, va al home, y solo ahí ve si el cotizador funciona con sus valores. **No hay feedback inmediato de "lo que acabás de configurar hace esto"**.
5. **Doble onboarding**: el técnico (InitialConfig) y el marketing (OnboardingPage 4 slides) son flujos separados. Después del técnico, el usuario ve 4 slides que no agregan valor nuevo (los textos son generales, no referencian lo que acaba de configurar).
6. **Defaults sin contexto**: "200%" y "0.7" aparecen precargados sin indicación de que son "típicos" o recomendados. El usuario no sabe si los debe cambiar.
7. **Skip confuso**: "Lo agrego después" en filamento aparece como un `TextButton` debajo del formulario, visualmente débil. El usuario puede no entender que filamento es opcional.

El usuario pidió **"rediseño completo"**. Este feature rehace el flow manteniendo **funcionalmente** los 6 inputs (idioma, moneda, impresora, filamento, profit %, kWh) pero mejorando estructura, microcopy, feedback visual y la transición al home.

## 2. User Story

**Como** maker/operador de impresión 3D que abre la app por primera vez

**Quiero** que la configuración inicial sea un flow corto, visualmente guiado, con microcopy que explique por qué se pide cada input, con feedback inmediato de que lo que estoy configurando afecta mi cotizador, y sin pasar por un "marketing tour" separado después

**Para** terminar de configurar en menos de 90 segundos sintiendo que la app ya está lista para cotizar, y entrar al home con confianza.

## 6. Decisiones de diseño clave

### 6.1 Flow alternativo: 3 opciones con pros/contras

> El usuario pidió "rediseño COMPLETO" — esto significa que tiene que elegir entre alternativas. Las 3 opciones son **mutuamente excluyentes** y la decisión define el alcance visual.

---

#### **Opción A — Single-page scrollable (form vertical largo)**

Una sola pantalla con `SingleChildScrollView` que muestra las 6 secciones en cards apiladas. Sin stepper, sin AnimatedSwitcher entre pasos. Cada card es una "sección colapsable opcional" o todas abiertas a la vez.

**Layout propuesto**:

```
┌──────────────────────────────────────┐
│  [logo 3dCal]                        │
│  Configura tu app                    │
│  <subtítulo 1 línea>                 │
├──────────────────────────────────────┤
│  ⓘ  Idioma y moneda                  │  ← card siempre visible
│     [SegmentedButton ES/EN]          │
│     [DropdownButton moneda]           │
├──────────────────────────────────────┤
│  🖨  Tu impresora                    │  ← card requerida
│     [BrandSelectorField]             │
│     [TextField modelo]               │
│     [NumericField watts]             │
├──────────────────────────────────────┤
│  🧵  Tu filamento (opcional)         │  ← card con skip
│     [BrandSelectorField]             │
│     ...                              │
│     [ Lo agrego después ]            │
├──────────────────────────────────────┤
│  💰  Ganancia y energía              │
│     [NumericField 200%] [chip típico]│
│     [NumericField 0.7]   [chip típico]│
├──────────────────────────────────────┤
│        [ Empezar a cotizar → ]       │
└──────────────────────────────────────┘
```

**Pros**:
- Cero stepper → implementación más simple (menos estado, menos transiciones).
- Todo visible de un vistazo. El usuario no se pregunta "qué viene después".
- En web (desktop), el scroll vertical es natural.
- Mobile scroll es aceptable si las cards son cortas.

**Contras**:
- En mobile portrait puede ser largo (8+ pulgadas de scroll). Sensación de "formulario de registro web".
- Sin progreso visible → el usuario no sabe cuánto falta.
- Si el usuario tiene prisa, puede hacer tap en "Empezar" sin haber llenado todo (error de UX).

**Cuándo elegir A**: si el usuario quiere simplicidad máxima y está OK con scroll largo en mobile.

#### **Opción C — Wizard conversacional / chat-style**

Una pantalla que muestra **una pregunta a la vez**, con transiciones suaves, microcopy grande, y un botón gigante "Continuar". Estilo "Duolingo" o "Typeform".

**Layout propuesto**:

```
┌──────────────────────────────────────┐

│                                      │

│                                      │

│                                      │

└──────────────────────────────────────┘
```

**Pros**:
- Más gamificado, engagement mayor.
- Preguntas enfocadas → menos overwhelm.
- "Saltar" más explícito.

**Contras**:
- 6 pasos = 6 transiciones. Más lento en términos de taps.
- Menos información contextual visible por paso.
- Requiere `AnimatedSwitcher` o `Hero` por pregunta, más código.
- Rompe el patrón del resto de la app (que usa M3 stepper-like en otros lugares).
- No recomendado para apps técnicas: el usuario quiere ver progreso técnico, no un tour.

**Cuándo elegir C**: si el usuario quiere gamificar el onboarding (más "consumer app" que "tool").

### 6.2 Mi recomendación: **Opción B**

Razones:
1. **Mantiene familiaridad**: el usuario que ya vio el stepper actual (o que viene de un reinstall) reconoce el patrón.
2. **Mobile-first**: 3 cards que caben en pantalla con scroll interno es el sweet spot para portrait.
3. **Coherencia con el design system**: usa Material 3 nativo (`LinearProgressIndicator`, `Card`, `FilledButton`).
4. **Migración incremental**: si después se quiere ir a Opción C, los datos y los componentes ya están desacoplados.
5. **Tiempo de implementación**: ~2x vs mantener el stepper actual, pero < Opción C.

### 6.3 Indicador de progreso

- **Recomendado**: `LinearProgressIndicator` M3 con `value: (_step + 1) / _totalSteps`, debajo del título.
- **NO recomendado**: mantener el `_StepperIndicator` custom (líneas 556–662). Es código custom que rompe la coherencia M3 y requiere mantenimiento separado.
- **NO recomendado**: `Stepper` widget de Material (`material.Stepper`) — es horizontal/vertical y no encaja con el flujo compacto mobile.

### AC-001 — Indicador de progreso Material 3 nativo
- **Scenario**: el usuario abre la app por primera vez.
- **Action**: observar el header de `InitialConfigPage`.
- **Expected**:
  - Hay un `LinearProgressIndicator` (o equivalente M3 nativo) debajo del título, con `value: (_step + 1) / _totalSteps` que avanza de 0.0 → 0.33 → 0.67 → 1.0 según el paso.
  - El `_StepperIndicator` custom (con círculos + checkmarks) **ya no existe** en el código.
- **Must not**:
  - El indicador **NO** es el widget `_StepperIndicator` (verificar con grep en el código final).
  - El indicador **NO** muestra números romanos, círculos numerados, ni checkmarks.
- **Verification**: `grep -r "_StepperIndicator" lib/` retorna 0 resultados en el archivo `initial_config_page.dart`. Visual review.
- **Priority**: Required

---

### AC-002 — Cada sección tiene microcopy "por qué"
- **Scenario**: usuario navega por los 3 pasos.
- **Action**: leer los helpers de cada sección.
- **Expected**:
  - Idioma: helper explica que es elegible post-config.
  - Moneda: helper explica que NO convierte valores (importante para Bolivia con multi-moneda).
  - Impresora: helper explica "para qué" (costo de energía).
  - Filamento: helper explica que es opcional.
  - Ganancia %: helper explica que 200% duplica y muestra rango típico.
  - kWh: helper explica "para qué" y muestra rango típico para Bolivia.
- **Must not**:
  - Ningún helper es **vacío** (todos los inputs tienen al menos una línea de explicación).
  - Ningún helper es **técnico/jerga** sin contexto (no "wireless sync", no "API").
- **Verification**: visual + test que verifica que cada `TextFormField` / `NumericInputField` tiene un `helperText` no vacío.
- **Priority**: Required

---

### AC-003 — Defaults con tag "Típico"
- **Scenario**: usuario llega al paso 3 (ganancia y energía).
- **Action**: observar los 2 campos numéricos.
- **Expected**:
  - El campo de ganancia muestra el valor `200` y un `Chip` o `Badge` "Típico" al lado (o debajo).
  - El campo de kWh muestra el valor `0.7` y el mismo tag "Típico".
  - Si el usuario cambia el valor (ej: `250` para ganancia), el tag desaparece.
  - Si el usuario vuelve al valor default, el tag reaparece.
- **Must not**:
  - El tag **NO** aparece como texto inline largo (es un chip/badge pequeño).
  - El tag **NO** dice "Default" (en inglés) ni "Recomendado" (es ambiguo en es_BO).
- **Verification**: widget test que verifica que con `value == 200`, hay un widget con texto `settingsDefaultTypical` ("Típico"), y con `value == 250`, no.
- **Priority**: Required
