## Context

tresdcal es una calculadora de precios para impresiones 3D, 100% local (sin backend, sin auth server-side), corriendo en Android/iOS/Web. Hoy todas las features son gratuitas y estan implementadas de extremo a extremo: single + multi-material calculator, branding (logo + nombre de empresa) que aparece en PDF y en home, historial completo de cotizaciones, export PDF y CSV, catalogos de filamentos e impresoras sin limite, dashboard con monthly totals y top materials.

El user quiere lanzar free en stores y gatear un subset de features detras de un pago. Las features que el user nombro (branding, cotizacion avanzada, historial, export) son todas implementadas y funcionales — el trabajo es decidir que se mueve a pro, agregar el modelo de entitlement, y conectar IAP/license. No hay ninguna infra de pago en el codigo hoy (ni `in_app_purchase`, ni `purchases_flutter`, ni nada cloud).

**Constraints duros del proyecto** (de `docs/PROJECT.md` + inspeccion):
- Sin backend. Cero.
- 3 plataformas: Android, iOS, Web.
- Web no puede usar IAP nativo de Apple/Google.
- Stack actual: Flutter 3.12, Drift, Riverpod, shared_preferences. Sin nada cloud.

## Objective

Habilitar modelo free/pro en tresdcal con:
1. **Gates visibles** que diferencien free vs pro sin romper la usabilidad del free.
2. **Monetizacion en mobile** (Android + iOS) via IAP nativo de stores.
3. **Solucion web** compatible con constraint no-backend.
4. **Modelo de entitlement local** que persista de forma robusta y permita restore.

El work esta completo cuando: un user puede comprar "Pro" en mobile, ver features pro inmediatamente, restaurar su compra en otro device, y todo el sistema se mantiene sin backend. Web tiene una estrategia definida (no necesariamente IAP).

## Out of Scope

- **Subscriptions con renovacion automatica** — se puede agregar despues, MVP es one-time unlock. Razon: simplicity + sin backend que maneje webhooks de renovacion.
- **Multi-tier (Basic/Pro/Premium)** — solo dos tiers. Razon: scope creep. Si free/pro no alcanza, se itera.
- **Server-side receipt validation robusta** — para MVP mobile, validar localmente. Trade-off: ~5% de piracy aceptable vs. semanas de infra.
- **Analytics de conversion** (funnel, A/B test de paywall) — sin backend, sin analytics. Se puede agregar despues via Mixpanel/amplitude si hace falta.
- **Family Sharing** (Apple) / **multi-account sharing** (Google) — fuera de scope MVP. Se puede agregar como configuracion de entitlement mas adelante.
- **Promo codes / introductory pricing** — lo maneja cada store, no requiere codigo de la app.
- **Refund flow custom** — el user pide refund via store, el store maneja. La app solo necesita invalidar el entitlement cuando `verifyPurchase()` falla en restore.
- **Sincronizacion cross-device de entitlement via cloud** — no sin backend. El user usa "Restore" en cada device nuevo.
- **Localizacion de paywall a mas de es/en** — MVP solo es-AR/es-BO. Strings externalizados en `l10n/` para agregar mas despues.

## Monetization Options — Comparison

| Opcion | Mobile | Web | Costo | Complejidad | Sin backend | DRM | Recomendacion |
|---|---|---|---|---|---|---|---|
| **A. IAP nativo** (`in_app_purchase`) | ✓ (Play/App Store) | ✗ | 0 (15-30% fee del store) | Media — setup Billing Client + StoreKit + receipt parse | ✓ (offline validate, limitaciones) | Baja | **Recomendada para mobile** |
| **B. RevenueCat** (`purchases_flutter`) | ✓ (abstrae A) | △ (web SDK existe pero requiere cuenta cloud) | 0 hasta $2.5K MRR | Baja — SDK maneja todo | Parcial — dashboard cloud | Media | **Recomendada si user quiere A pero sin escribir boilerplate de stores** |
| **C. One-time unlock con license key** (pattern offline) | ✓ | ✓ | Bajo (Stripe/Lemon Squeezy) | Baja — input field + format check | ✓ (zero) | Muy baja | **Recomendada para web si se quiere consistencia cross-platform** |
| **D. Lemon Squeezy / Paddle** (Merchant of Record) | ✓ (web checkout → app unlock) | ✓ | Fee del MoR (~5%) | Media — web checkout + return URL + key claim | ✓ (ellos son el backend) | Media | **Recomendada si web monetization es prioritaria** |
| **E. "Honesty system"** (boton "Soy Pro" sin validar nada) | ✓ | ✓ | 0 | Trivial | ✓ | Nula | **No recomendada** — efectivamente gratis |

**Recomendacion principal**: **Opcion B (RevenueCat) para mobile + Opcion C (license key) para web**, con arquitectura que permita migrar.

Por que:
- RevenueCat es 0$ hasta $2.5K MRR. SDK Flutter oficial (`purchases_flutter`). Maneja restoration, validacion, subscription tracking. Para MVP, un product `tresdcal_pro_lifetime` non-consumable.
- Web recibe el mismo entitlement via license key. User compra via Lemon Squeezy hosted page (sin backend nuestro, ellos manejan), recibe codigo por email, lo ingresa en app web. La app web valida formato (no se puede validar "pago" sin backend). El codigo es un `uuid` que matchea uno en una lista firmada — pero sin backend, la "lista" la embebemos en la app y rotamos por version. Tradeoff conocido.
- **Alternativa simple**: web = todo gratis (no se gatea en web). Mobile = solo RevenueCat. Esto es lo que recomiendo si "consistencia cross-platform" no es prioridad — ver Open Questions Q3.

**Como saber quien pago (sin backend)**:
- Mobile: `purchases_flutter` (RevenueCat) o `in_app_purchase` expone `CustomerInfo` con `entitlements.active['pro'] != null`. Se persiste localmente en Drift (`entitlements` table) + cache en `shared_preferences` para boot rapido.
- Web: license key se guarda en `localStorage` (web) o Drift (si hybrid). Format validation client-side. Si rotamos keys, hay versionado en la key (`v1-{uuid}`).

**Restore purchases**:
- Mobile: `Purchases.restorePurchases()` (RevenueCat) o `InAppPurchase.restorePurchases()`. Apple lo requiere por guideline. Failure: mostrar mensaje "No hay compras para restaurar".
- Web: no aplica (no hay purchase que restaurar — la license key se re-ingresa manualmente).

## Data Model

### Drift table `entitlements`

```dart
@DataClassName('Entitlement')
class Entitlements extends Table {
  IntColumn get id => integer().autoIncrement()();
  TextColumn get productId => text()();                    // 'tresdcal_pro_lifetime'
  TextColumn get source => text()();                        // 'play' | 'appstore' | 'license_key'
  TextColumn get licenseKey => text().nullable()();         // null para IAP
  TextColumn get purchaseToken => text().nullable()();      // null para license_key
  DateTimeColumn get originalPurchaseDate => dateTime()();
  DateTimeColumn get expiresAt => dateTime().nullable()();  // null = lifetime
  DateTimeColumn get validatedAt => dateTime()();
  IntColumn get schemaVersion => integer().withDefault(const Constant(1))();
}
```

### SharedPreferences cache (boot-time fast path)

```dart
// Key: 'is_pro' -> bool
// Key: 'entitlement_source' -> String?
// Key: 'entitlement_validated_at' -> ISO timestamp String
```

### Why both?

- Drift: source of truth, auditable, queryable, backup-friendly.
- SharedPreferences: read en `main()` antes de que la DB este lista. UI arranca con `isPro=true` si el cache dice eso, evita flicker.

### Schema migration

`AppDatabase.schemaVersion` actualmente es 4. Bump a 5 en este feature. Migration:


### Receipt validation strategy

- **Mobile (RevenueCat path)**: `Purchases.getCustomerInfo()` valida contra el backend de RevenueCat (ellos validan contra Apple/Google). Cacheamos el resultado en Drift. Si falla la red, mantenemos el cache por 7 dias (configurable en RevenueCat dashboard).
- **Mobile (in_app_purchase directo)**: `InAppPurchase.verifyPurchase` es local-only validation. Limitacion: ~5% piracy. Aceptable para MVP.
- **Web (license key)**: format validation client-side. Key = `v1-{uuid}-{checksum}`. Si checksum OK y UUID en lista embebida (rotamos por version de app), validar. Sin backend, esto es seguridad theatre pero suficiente para MVP.
